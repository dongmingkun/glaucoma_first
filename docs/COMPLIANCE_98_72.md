## 2. T4 延迟

### 2.1 稳态（与 `cost.py` 口径对齐）

模型加载一次，逐图 `run_group([path], batch=1, workers=1)`，100 图：

```text
p50 72.99 ms | p95 80.42 ms | mean 73.98 ms
```

与 #97 在 RTX 5060 上记录的 p95 77.2–80.7ms 基本重合，T4 上同样落在线内。

### 2.2 冷进程 CLI（含加载）

`python predict.py --csv test100.csv --images images100 --weights ×3 --tta 1 --batch-size 1` 三次：

```text
14.932 s / 14.571 s / 14.601 s  →  147.01 ms/图（min 145.71，max 149.32）
```

其中约 6.7 s 是模型加载/CUDA 初始化（约 3 s）与 100 次 Kaggle 挂载路径 stat（约 3 s），
摊到 100 图约 67ms/图。**不能把 147ms 当作"单图 147ms"**，
也不能把 80ms 当作"含冷启动"——两个口径同时给出，避免误读。

### 2.3 全量 5855

CLI wall 531.4 s = 90.76 ms/图；其中：

- 推理循环（predict.py 自计）358 s = **61.1 ms/图**；
- 一次性图像索引 **约 166 s**：5855 个 `os.path.exists` 打在 `/kaggle/input` 挂载的 dataset 符号链接上，
  每次 stat 约 28ms；本地磁盘上这一步可忽略。

即使把 166 s 全部计入，90.76 ms/图 仍在 100ms 内。

## 4. 不能证明什么，以及缺什么

### 4.1 cache512 输入 ≠ 官方原图

Kaggle 数据集 `linglingyusc/glaucoma` 只提供 `cache_all/test`（512px 缓存 jpg，5855 张），**没有原始图**。
包的标准前处理是「原图 draft 解码 → 眼底内容裁剪 → cache_size 缩放」，在缓存图上会再走一次裁剪/重编码，
概率因此漂移。后果：

- 全量 CSV md5 `ae4200bf296276a834516cbf2e72c26e`（sha256 `d2447a74…`）**不能与台账 98.72 的 `b664…` 比对**，
  不相等不代表包有问题；
- 与 ens10（98.82 的固化件）对比：rank Spearman **0.9431**、标签一致率 **97.54%**、均值 0.0527（ens10 为 0.0830）。
  这个一致性偏低，进一步说明**缓存输入不等价，这份 CSV 不能提交**，只能作为"管线跑通 + 格式正确"的证据。

### 4.2 要闭环还需要

| 缺件 | 用途 | 补齐后动作 |
|---|---|---|
| 5855 张 test 原图 | 用同一包跑官方前处理 | 重跑并核对 md5 是否 `b664…`；再做 100 图官方 CSV 比对 |
| 队长处 98.72 官方 `submission.csv` | 逐行对比 | 100/5855 行二值一致率 + max\|Δp\| |

在没有原图的情况下，任何"98.72 复现成功"的声明都缺少输入侧证据；本文件只声明时延、包体、F2 与格式。
